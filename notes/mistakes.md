## Hash

### 1. Two Sum

暴力解写内层循环时，两次都栽在 `enumerate` 的计数起点上：

- `for j, y in enumerate(nums)`：内层每轮从 0 开始，`j` 可能等于 `i`，同一个元素被用了两次。前面写的 `j = i + 1` 会被 `for` 立刻覆盖，不起作用。
- `for j, y in enumerate(nums[i+1:])`：切片是新列表，`j` 从 0 计数，原数组下标应为 `i + 1 + j`，却返回了 `i + j`。

教训：`enumerate` 给的是当前遍历对象里的位置，不一定是原数组下标。需要控制起点时用 `range(i + 1, n)`，或 `enumerate(..., start=...)`。

### 49. Group Anagrams

**选 key**

- 用字符编码之和作 key：`"ad"` 和 `"bc"` 都是 197，不同组被分到一起。key 必须满足「同组一定相同、不同组一定不同」，求和只满足前一半。
- `sorted(s)` 返回 list，直接作 key 报 `unhashable type: 'list'`。要转成 `"".join(sorted(s))` 或 `tuple(sorted(s))`。

**dict / list 的返回值**

- `d.get(key, []).append(s)`：默认值只是返回一个临时列表，不会存进字典，字典始终为空。要用 `d.setdefault(key, []).append(s)` 或 `defaultdict(list)`。
- `d[key] = d[key].append(s)`：`list.append` 原地修改、返回 `None`，这样会把值覆盖成 `None`。
- `return d.values` 少了括号，返回的是方法本身；而且 `.values()` 是视图，要 `list(...)`。

**写法习惯**

- 条件里用 `&` 代替 `and`：`&` 是按位与、不短路，右边的 `sorted` 总会被执行。
- `n = len(s)` 放到定义 `s` 的循环前面，导致 `NameError`。
- 又用了 `str`、`dict`、`sum` 作变量名（Two Sum 里用过 `dict`），遮蔽内置名字。

**易错点：`for ... else` 里的 `break`**

暴力解把 `ff` 标志位换成 `for ... else` 后，`break` 不能删：`else` 只在循环没被 `break` 时执行，删掉后每个串都会额外新开一组，`["eat", "tea", "ate"]` 会得到 `[['eat', 'tea', 'ate'], ['tea', 'ate'], ['ate']]`。标志位写法里 `break` 只是提前结束，删掉结果仍然正确。

### 128. Longest Consecutive Sequence

**复杂度**

- 用 `min(set)` 找每段的起点：`min()` 是线性扫描，每段调用一次。输入全是互不相邻的数时段数等于 n，退化成 O(n²)，实测 4 万个数要 23s。判断段首应该用 `num - 1 not in s`，O(1)。
- 外层遍历 `nums` 而不是去重后的 `set`：重复的段首会让同一段被反复数。`[1] * 50000 + list(range(1, 50001))` 这种输入直接退化成 O(n²)。

**边界**

- `cur_len` 从 0 开始计数，结果比实际长度少 1。段首本身要算一个。

**易错点：剪枝不是普通的提前返回**

LeetCode 上的快解里有 `if max_length > len(s) // 2 + 1: return max_length`。它成立的前提是各段互不重叠，剩下的元素不够组成更长的段。这类提前返回必须能证明「后续不可能更优」，否则就是 bug；它省的是计算量，和用 `return` 代替 `else` 那种写法层面的提前返回不是一回事。

## Two Pointers

### 283. Move Zeroes

**第一版：边找边清 0**

- 外层条件写成 `while sec != n - 1`：`[0,1,0,3,12]` 扫到 `sec = 4` 就退出，`12` 没被搬，得到 `[1,3,0,0,12]`。而且内层 while 可能让 `sec` 直接跳过 `n - 1`，`!=` 永远成立。
- 内层 `while nums[sec] == 0` 没检查边界：`[1,2,0,0]`、`[0,0,0]` 这种末尾全是 0 的输入直接 `IndexError`。
- 先 `nums[fst] = nums[sec]` 再 `nums[sec] = 0`：`fst == sec` 时两步作用在同一个位置，把非零数清成 0，`[1,2,3]` 得到 `[0,0,3]`。

**第二版：一次遍历的交换写法**

- 判断条件写成 `nums[sec] != nums[fst]`：该看 `nums[sec]` 是不是 0，却和 `fst` 位置的值比较。0 被当成非零搬到前面，`[1,2,3]` 里 `fst` 不前进，`1` 被覆盖丢失。这是 26 题「删除有序数组中的重复项」的判断方式，两题的双指针形状一样，但「保留谁」的条件不同。
- 去掉了补 0 的循环，却仍然只覆盖不交换：`sec` 位置的旧值没人处理，`[0,1,0,3,12]` 得到 `[1,0,3,12,12]`。

教训：快慢指针的写法要回答两件事：`fst` 的含义（下一个非零数该放的位置），以及 `sec` 位置的旧值去哪（补 0 或交换）。用 `for sec in range(n)` 代替手动移动 `sec`，边界问题自然消失。

**易错点：操作次数和数据分布有关**

实测 n = 1 万时的写入次数：覆盖 + 补 0 固定写 n 次；交换写法在 99% 是 0 时只写 208 次，但只有开头一个 0 时要写 19998 次（差不多是前者两倍）。两种都是 O(n)，没有哪种在所有分布下都更少。

### 11. Container With Most Water

**写法**

- 暴力解第一版忘了 `return res`，函数返回 `None`。
- 双指针解命名为 `SolutionDoublePointer`，没有类叫 `Solution`，测试跑到性能用例时 `NameError`。最终提交的解法必须叫 `Solution`。
- 循环条件写成 `abs(l - r) >= 1`，并且先移动再算面积：`l` 始终不大于 `r`，`abs` 多余；指针相遇后还会再算一次宽度为 0 的面积。先算面积再移动，条件用 `l < r` 即可。

**易错点：为什么可以丢掉矮边**

只说「水位受限于矮边」不够，还要加上宽度。设 `height[l] <= height[r]`，对任意 `l < j < r`：

```
min(height[l], height[j]) * (j - l) <= height[l] * (j - l) < height[l] * (r - l)
```

高度不超过矮边，宽度一定更窄，所以以 `l` 为一端的剩余组合都不超过当前面积。两边一样高时这个不等式对 `l` 和 `r` 都成立，移动哪边、或两边一起移动都对（实测三种写法都通过 500 组随机数据）。

**常数优化：跳过不高于矮边的线**

第一版优化写成了下面这样，四处错误：

- `res = cur > res ?? res : cur`：Python 没有 `?:`，要写 `a if cond else b`；而且按 C 的语义理解方向也反了，`cur=10, res=3` 会留下 `3`。
- `cur = h * (r - l)` 写在循环第一行，`h` 要到分支里才赋值，第一轮 `UnboundLocalError`。就算 `h` 有值，也是上一轮矮边的高度，和跳过之后的 `r - l` 对不上。`cur` 要在跳过**之前**、用**本轮**矮边来算。
- `else` 分支从 `if` 分支复制过来，移动 `r` 却判断 `height[l] <= h`：`height[l] > height[r]` 时条件不成立、`r` 不动，`[2, 1]` 死循环；两边相等时 `height[l]` 不变，`r` 一路退到 `l`，`[1, 5, 5, 1]` 得到 3（期望 5）。
- 直接覆盖掉了原来的解法，没有保留。

教训：对称的两个分支复制后，逐个检查变量名是否都换成了另一侧。

**易错点：常数优化要看数据分布**

n = 10^5，每种跑 15 次取最快：

| 分布 | 原双指针 | 去掉 `min()` | 跳过不高于矮边的线 |
|---|---|---|---|
| 随机 | 10.9 ms | 6.0 ms | 2.8 ms |
| 单调递增（有大量重复高度） | 11.1 ms | 6.0 ms | 3.4 ms |
| 高度全相同 | 10.8 ms | 6.0 ms | 2.6 ms |

但 n = 1 万、严格递增时一条线也跳不过：原写法 1.08 ms，去掉 `min()` 0.59 ms，跳过写法 0.92 ms。三者都是 O(n)，差别只在常数；跳过写法在本题快，是因为高度上限 10^4 远小于 n 上限 10^5，必然有大量重复高度可跳。

### 15. 3Sum

**去重思路**

- 想「找到一组就把这三个数从 `nums` 里删掉」：一个数可以属于多组不同的三元组，`[-2, 0, 1, 1, 2]` 里唯一的 `-2` 同时属于 `[-2, 0, 2]` 和 `[-2, 1, 1]`，删掉就漏；每个值只删一份又去不掉重复，`[-1, -1, 0, 0, 1, 1]` 会得到两次 `[-1, 0, 1]`。去重要靠「认出同一组」，不能靠「消耗掉数」。

**HashSet 解法**

- `sorted(tuple([...]))`：`sorted` 无论传什么都返回 list，结果不可哈希。应为 `tuple(sorted(...))`。
- 内层 `for sec in nums` 从头遍历，`seen` 放在两层循环外从不清空：`seen` 里含有 `fst` 自己和之前所有轮的数，`[-1, 2, 0]` 得到 `(-1, -1, 2)` 和 `(0, 0, 0)`。`seen` 必须只含 `i` 和 `j` 之间的数：每轮 `i` 新建，`j` 从 `i + 1` 开始，先查再放。
- 加了一行 `seen[last] = seen[last] - 1`，但判断用的是 `in`，只看键不看值，这行不起作用。

**双指针第一版**

- 第二个判断写成 `if total > 0` 而不是 `elif`：`total < 0` 时还会落进 `else`，把和为 -3 的 `(-4, -1, 2)` 加进结果。三种情况必须互斥。
- `total > 0` 分支写成 `while nums[l] == right: r -= 1`：移动 `r` 却判断 `nums[l]`，死循环。**和 11 题跳过优化那一版是同一个复制错误**，同时有 `l`/`left`、`r`/`right` 两套名字也让值和下标更容易对错边。
- 内层 while 没有 `l < r` 边界：`[-5, 1, 1]` 里 `l` 跳过所有 `1` 后越界。

**双指针第二版**

- 在 `for i in range(n)` 的末尾 `while nums[i] == a: i += 1`：下一轮 `range` 会重新给 `i` 赋值，跳过完全不生效。全是 0 时外层照跑 3000 轮、命中 450 万次。要么换成 `while` 自己控制 `i`，要么在开头 `if i and nums[i] == nums[i - 1]: continue`。
- `tuple(a, b, c)`：`tuple()` 只接受一个可迭代对象，报 `tuple expected at most 1 argument, got 3`。直接写 `(a, b, c)`。

**易错点：跳过重复要和前一个比**

`if nums[i] == nums[i + 1]: continue` 会漏解：`[-1, -1, 2]` 里第一个 `-1` 被跳过，第二个 `-1` 后面只剩 `2`，凑不出 `[-1, -1, 2]`。要保留相同值里的**第一个**（它后面的区间最大），跳过后面的，所以和 `nums[i - 1]` 比。

**易错点：`a > 0` 可以直接结束**

排序后 `b`、`c` 都不小于 `a`，`a > 0` 时和不可能为 0。n = 3000 全是正数时，内层从 437 万次降到 0 次（495 ms → 0 ms），大范围随机 483 ms → 362 ms。

**易错点：LeetCode 上的计数快解**

按「几个值相同」分类、只在不同值上枚举的解法（见题目文件 `SolutionCount`），n = 3000 随机数据约 30 ms，双指针 150 ~ 350 ms。复杂度没变，快在常数。原始代码有三个坑：

- 没有 `from bisect import ...`：LeetCode 预导入了常用模块所以能过，本地 `NameError`。
- `-value / 2` 是浮点数：`[-4, 2, 2]` 返回 `(-4, 2.0, 2.0)`。查字典碰巧对（`2.0 == 2` 且哈希相同），但结果类型错了。先判偶数再用 `//`。
- 返回 tuple 而不是 list。

**易错点：`s != 0` 分支里不需要跳过重复**

值不变时 `s` 不变，每轮都会做同样的移动，跳不跳结果一样；只有命中后不跳才会重复记录。没有重复值时，内层 while 每次只跳一步却多了赋值和判断，大范围随机 325 ms，只在命中后跳过为 186 ms。

### 42. Trapping Rain Water

**暴力解**

- 左边扫描写成 `l = 0; while l > -1: ...; l -= 1`：只读了 `height[0]`，每格的左边最高都是 0，示例得到 -13。
- 加上 `max(h_i, 0)` 后结果变成 0：取 0 本身没错，但把「左边最高永远是 0」的 bug 藏了起来。结果从负数变成 0 时，要先查为什么会有负数。

**两遍扫描**

- 第一版只从左往右扫一遍：扫过全局最高柱子后再没有更高的柱子，右边那一段水位一直是 0。示例得到 5（期望 6），`[3, 0, 2]`、`[5, 4, 1, 2]` 得到 0。要从右往左镜像再扫一遍。
- 判断写成 `height[r] > cur`：一样高的柱子不触发，`[2, 0, 2]`、`[3, 0, 0, 3]` 得到 0。两遍都用 `>` 时 4000 组随机错 892 组，改成 `>=` 全对。
- 水位列表先写成 `h = []`，又写成 `h = [n]`：前者是空列表，后者是「一个装着 n 的列表」，给 `h[j]` 赋值都 `IndexError`。固定长度要写 `[0] * n`。
- `max(height[k] - h[k], 0)` 减反了，积水是水位减柱子高度；`return h` 返回了水位列表而不是 `res`。

**双指针（没写错，整理时的常数优化）**

- 先用 `height[l]` 更新 `lmax` 再加水时，`lmax - height[l] >= 0` 恒成立，`max(..., 0)` 多余（5000 组随机里不取 0 的单格最小值正好是 0）。
- 每轮两边的最大值都更新，其中不移动的一边是白算的。只更新移动的一边、用 `if` 代替 `max()`：n = 2 万从 3.8 ms 降到 1.5 ms。

**易错点：LeetCode 显示的运行时间**

LeetCode 上一份显示 1 ms 的双指针和这里是同一个算法，本地只比未优化版快 20%（少了一次 `max(..., 0)`），比只更新一边的写法慢一倍。LeetCode 的时间是服务器上所有用例的总和，同一份代码多次提交会波动好几倍，比不出常数差异；比较写法要本地同数据多次取中位数。

## Sliding Window

### 3. Longest Substring Without Repeating Characters

- 窗口长度写成 `i - l`：窗口两端都包含，应为 `r - l + 1`，示例 `"abcabcbb"` 得到 2。
- 遇到重复直接 `l = last[c] + 1`：`last` 记的是全局上次出现的位置，不会随窗口移动删除旧记录，`c in last` 只说明以前出现过，不说明在窗口里。`'abba'` 最后一步 `'a'` 上次在 0，已在窗口 `[2, 3]` 左边，`l` 却从 2 退回 1，窗口里又有两个 `'b'`，得到 3（期望 2）；`'a b c a'` 得到 6（期望 3）。要么 `l = max(l, last[c] + 1)`，要么先判断 `last[c] >= l`。

教训：滑动窗口的两端都只往右走。任何让左端移动的赋值，都要确认新位置不小于旧位置。

**易错点：常数优化**

n = 5 万：`range(len(s))` + `s[r]` + 两处 `max()` 约 8.9 ms；改用 `enumerate` 取出 `c` 约 7.6 ms；再用 `if` 代替 `max()` 约 3.1 ms。复杂度不变。

### 438. Find All Anagrams in a String

- 字符转编码写成 `oct(c)`：`oct` 是把整数转成八进制字符串（`oct(8) == '0o10'`），传入字符报 `TypeError: 'str' object cannot be interpreted as an integer`。字符转编码是 `ord`，反过来是 `chr`。

**易错点：`Counter` / `dict` 计数减到 0 后的键**

窗口移出字符后计数变 0，键还留在字典里。本地 Python 3.9 的 `Counter({'a': 2, 'b': 0}) == Counter({'a': 2})` 为 `False`，3.10+（LeetCode）为 `True`；普通 `dict` 在任何版本都不相等。同一份代码 LeetCode 能过、本地失败。计数减到 0 时 `del`，或者只有小写字母时直接用 26 位数组。

**易错点：O(1) 比较在 Python 里收益很小**

维护「还有几个字母次数没对上」可以把每步比较降到 O(1)，但 n = 3 万时实测 3 ~ 5 ms，26 位数组直接 `==` 比较 4 ~ 6 ms：长度 26 的列表比较在 C 层完成，比多写的几个 Python `if` 更快。
